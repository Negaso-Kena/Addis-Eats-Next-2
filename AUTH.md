# Authentication, authorization, and ownership

This is a teaching demo with in-memory users and orders. Demo credentials are
not production credentials; they are public course accounts stored as bcrypt
hashes in `lib/demo-users.json` (generated by `scripts/setup-demo-users.mjs`). Sessions use signed, stateless cookies so they can
be verified consistently across serverless instances.

## Private routes and actions

| Surface | Middleware | Server/page check | Data/action check |
| --- | --- | --- | --- |
| `/checkout` | Requires a `session` cookie | `app/checkout/page.js` calls `getSession()` and redirects if invalid | Confirmation uses `getOrderForUser(orderId, user.id, user.role === "staff")`; `placeOrder` independently requires `getSession()` and assigns the owner from `user.id` |
| `/orders` | Requires a `session` cookie | `app/orders/page.js` calls `getSession()` | Customer list uses `getOrdersByUserId(user.id)`; staff list is intentionally all orders |
| `/orders/[id]` | Requires a `session` cookie | `app/orders/[id]/page.js` calls `getSession()` | `getOrderForUser(id, user.id, user.role === "staff")` returns only an owned order, unless staff |
| `/dashboard` | Requires a `session` cookie | `app/dashboard/page.js` requires a valid session with `role === "staff"` before any order is read or aggregated | Read-only; no mutation actions. A customer sees "Staff access required" and no chart data. |
| `/kitchen` | Requires a `session` cookie | `app/kitchen/page.js` requires a valid session with `role === "staff"` | There are no kitchen mutation actions in this app. |
| `GET /api/orders` | Not run on API routes | Handler calls `getSession()` | Customer list is filtered by `user.id`; staff may see all. |
| `POST /api/orders` | Not run on API routes | Handler calls `getSession()` | Validates the body, recomputes prices, and uses `user.id`; it never accepts an owner id. |
| `GET /api/orders/[id]` | Not run on API routes | Handler calls `getSession()` | `getOrderForUser(id, user.id, user.role === "staff")`; unauthorized and missing orders both return 404. |
| `cancelOrder` server action | Not applicable to actions | `getSession()` inside the action | `cancelOrderForUser(id, user.id, user.role === "staff")`: the lookup is scoped, so another customer's id finds nothing; refused once the order is On the way or Delivered |
| `signIn` server action | Public by design | Verifies demo credentials against bcrypt hashes | Creates a session and validates `next` as a same-origin relative URL. |
| `signOut` server action | Public by design; signing out is safe for any caller | Expires the signed session cookie | |

The request gate in `proxy.js` is a navigation gate, not authentication:
it checks only that a cookie exists. The page, action, and API layers verify
the cookie signature and expiration, then map its user id to a known user.
Customer ownership checks are performed in the store lookup itself, not only
after returning an order by id.

The three checks have different jobs:

1. Middleware redirects protected page requests that have no session cookie.
   A fabricated cookie can pass this gate, so this is not proof of identity.
2. The server page/action calls `getSession()` and verifies the signed token
   and maps its user id to a known user; `/kitchen` also verifies the staff role.
3. The data/action layer checks order ownership and validates/recomputes order
   data. API routes do their own session checks because middleware does not run
   for them.

Do not describe the middleware check by itself as authentication. The signed
session token works across serverless instances, but the demo user directory
and order data still use process-local memory and are not shared or durable.

The session cookie is set with `httpOnly`, `sameSite: "lax"`, root path, and
an eight-hour lifetime (`SESSION_TTL_SECONDS` in `lib/session.js`); `secure` is enabled in production. The token contains
only a user id and timestamps, is integrity-protected with HMAC-SHA256, and
cannot be read by client JavaScript. Production must set `SESSION_SECRET` to
a unique random value of at least 32 bytes in Vercel's environment variables.
All instances that serve the same cookie domain must use the same value;
separate environments on different domains can use separate secrets. Never
commit the actual secret.
Local development uses a development-only fallback when the variable is absent.

Because sessions are stateless, signing out expires the browser's cookie but
cannot revoke a copied token before it expires. Changing `SESSION_SECRET`
invalidates every existing session. Per-session revocation requires a shared
durable session store.

## Attack checks

Run these against a running production build. Record the actual response and
the protecting layer when demonstrating them; do not count a hidden UI link as
authorization.

| Attack | Expected result | Protection to point to |
| --- | --- | --- |
| Sign out, then request `GET /api/orders` or `GET /api/orders/AE-2048` | `401 Not signed in` | `getSession()` checks in the API handlers |
| Sign in as a customer, then request another customer's order ID through `/orders/[id]`, `/api/orders/[id]`, or `/checkout?order=<id>` | 404/no order details | `getOrderForUser` enforces ownership during lookup; checkout never renders another user's confirmation |
| Request `/signin?next=https://example.com` or `/signin?next=//example.com`, then sign in | Redirect to `/` | `getSafeRedirectPath` in `app/auth-actions.js` rejects cross-origin destinations |
| Submit `cancelOrder` signed out, or as a different customer | Signed out: refused by the request gate; other customer: error, order unchanged | `getSession()` and the scoped `cancelOrderForUser` lookup |
| Submit `placeOrder` without a valid session | Action refuses; no order is saved | `getSession()` at the start of `app/actions.js` |
| Sign in as a customer and navigate directly to `/kitchen` | Staff access denied | Role check in `app/kitchen/page.js` |
| Sign in as a customer and navigate directly to `/dashboard` | Staff access denied, no chart or table data in the response | Role check in `app/dashboard/page.js` |
| Open another customer's (or a demo) order at `/orders/<id>` | 404 | Scoped lookup in `getOrderForUser` |
| Send a forged `userId` in `POST /api/orders` | Saved order owner remains the session user | API handler sets `userId: user.id` after validating input |

For the cross-user check, place an order while signed in as `0911223344`, copy
the resulting `AE-...` id, sign out, sign in as the ownership-test customer,
then request `/orders/<id>`, `/api/orders/<id>`, and
`/checkout?order=<id>`. The detail page must be not-found, the API must return
404, and checkout must not reveal the confirmation. Repeat with the original
customer to confirm that their order remains accessible.

### Local production verification

Verified against `npm start` after a successful Webpack production build:

- Signed-out `GET /api/orders` returned 401; signed-out `/orders` and
  `/kitchen` redirected to sign-in.
- Signing in with an external `next` destination redirected to `/`, not the
  external host.
- An order owned by the first customer returned 404 from the other customer's
  order API and detail page; `/checkout?order=<id>` did not show the order
  confirmation.
- The second customer received an empty order list, and direct `/kitchen`
  navigation displayed the staff-only denial.

The order store is process-local, so order records are temporary and are not
retained after restarting the server.

The demo user directory and order store are in process memory. Order records
are lost on restart, and multi-instance/serverless deployments do not share
them. A real deployed application requires durable shared user and order data;
shared session storage is additionally required if immediate per-session
revocation is needed.

## Capstone additions

| Surface | Layers | What each proves |
|---|---|---|
| `GET /api/orders/[id]/stream` (server-sent events) | `getSession()` and `getOrderForUser(id, user.id, isStaff)` inside the handler, before the stream opens | Signed in, and the order is theirs (or they are staff). Signed out: 401. Someone else's id: 404. The stream also stops when the client disconnects. |
| `placeOrder` / `POST /api/orders` | Session inside the action; `requestId` makes a repeat submit return the same order | A double tap or retry cannot create a second order |
| `cancelOrder` | Session + scoped lookup | Customer: own orders only. Staff: any. Refused once On the way |
| `/orders` CSV export | Built from the same scoped list the table uses | A customer can only ever export their own orders |

The three attacks (see `PRESENT.md` for the exact steps) and the line that refuses each:

1. **Signed out** calls an order endpoint: `if (!user)` at the top of the handler or action.
2. **Signed in as someone else** asks for another customer's order id: the scoped lookup `getOrderForUser` / `cancelOrderForUser` finds nothing, so the answer is 404 and no data.
3. **Crafted return link** `/signin?next=https://example.com`: `getSafeRedirectPath` in `app/auth-actions.js` rejects anything that is not a plain internal path.
